# AI 법무관리시스템 제안서 웹페이지 설계

작성일: 2026-04-02

## 목표

제작요청서의 요구사항을 빠짐없이 반영한 제안서 웹페이지를 만든다. 이 웹페이지는 단순 소개 자료가 아니라 아래 두 역할을 동시에 수행해야 한다.

1. 대기업 고객 시연용 제안서
2. 내부 실행용 요구사항 추적 보드

핵심 성공 기준은 다음과 같다.

- 제작요청서의 주요 요구사항이 체크리스트로 모두 분해되어 있다.
- 각 요구사항이 `어느 페이지`, `어떤 화면`, `어떤 시연 방식`으로 반영되는지 즉시 확인할 수 있다.
- 사이트 자체가 엔터프라이즈 SaaS 제안서처럼 보이며, 실제 프로토타입 화면 방향을 설득력 있게 보여준다.
- IA, 화면 구성, 데모 플로우, 기술 스택, 범위/제외 범위, 일정 전략이 한 흐름으로 연결된다.

## 명시적 가정

- 현재 저장소는 비어 있으며, 기존 코드나 디자인 시스템은 없다.
- 이번 작업의 1차 목적은 실제 프로토타입 제품 구현이 아니라 제안서 웹페이지 구현이다.
- 요청서의 핵심은 완성형 백엔드가 아니라 시연 수준의 UX 설계와 범위 해석이다.
- 테스트는 자동화로 검증해야 하므로 UI 렌더링 검증과 핵심 내용 존재 검증을 포함한다.
- 웹 E2E는 Playwright를 사용한다.

## 요구사항 해석

### 1. 무엇을 제안해야 하는가

고객은 단순한 “AI 계약서 분석기”를 원하지 않는다. 대기업 환경에서 실제로 도입 가능한 법무관리시스템의 구조를 짧은 데모로 이해하고 싶어 한다. 따라서 제안서는 다음 두 축을 동시에 보여줘야 한다.

- AI 기반 계약 분석/검토 UX
- 조직, 권한, 결재, 기준관리까지 포함하는 엔터프라이즈 운영 구조

### 2. 무엇이 더 중요한가

문서상 우선순위는 다음과 같이 읽힌다.

1. 조직도 및 권한 관리
2. 결재 프로세스 빌더
3. 체크리스트 / 플레이북 관리 및 AI 리뷰 반영
4. 계약서 업로드 + AI 메타데이터 추출 + 계약 상세
5. 대시보드
6. 자연어 계약 검색

즉, 고객 설득 포인트는 “AI가 똑똑하다”보다 “대기업 통제 구조 속에서 자연스럽게 돌아가는 제품처럼 보인다”에 가깝다.

### 3. 제안서 웹페이지가 반드시 해결해야 하는 질문

- 왜 이 범위를 한 달 내에 구현 가능하다고 보는가
- 어떤 화면을 어떤 우선순위로 제작할 것인가
- IA 상에서 이번 시연 범위가 어디인가
- 무엇은 진짜 구현하고 무엇은 더미/하드코딩으로 처리하는가
- 시연 때 어떤 순서로 보여주면 고객이 가장 잘 납득하는가

## 추천 구현 방향

### 접근 방식

`제안서-프로토타입 결합형`으로 간다.

- 메인 페이지는 롱스크롤 제안서 형식으로 설계한다.
- 각 주요 섹션에 실제 프로토타입 방향을 보여주는 프리뷰 패널을 붙인다.
- 보조 페이지를 통해 IA, 화면 전략, 체크리스트, 데모 시나리오를 상세히 보여준다.

### 사이트 정보 구조

- `/`
  - 제안 개요
  - 프로젝트 이해
  - 핵심 제안 포인트
  - 구현 범위 / 제외 범위
  - 핵심 화면 전략
  - 일정 및 수행 방식
  - 기술 스택 제안
  - 산출물
  - 왜 이 접근이 적합한가
- `/ia`
  - 전체 시스템 IA
  - 사용자 영역 / 관리자 영역 구분
  - 프로토타입 범위 하이라이트
  - 향후 확장 범위 표시
- `/screens`
  - 화면별 목적
  - 화면별 시연 포인트
  - 우선순위
  - 더미 데이터 전략
- `/checklist`
  - 요청서 원문 기반 체크리스트
  - 상태
  - 반영 위치
  - 시연 방식
  - 우선순위
- `/demo-flow`
  - 실제 고객 시연 흐름
  - 단계별 메시지
  - 연결 화면

## 체크리스트 모델

모든 요구사항은 아래 스키마로 관리한다.

- `id`
- `category`
- `title`
- `source`
- `priority`
- `status`
- `page`
- `demoMethod`
- `notes`

`status`는 아래 값만 사용한다.

- `반영 완료`
- `반영 예정`
- `제외 범위`
- `제안 필요`

`category`는 아래로 나눈다.

- 프로젝트 목표
- 구현 방향
- 핵심 기능
- 우선순위
- 화면 구성
- 디자인 방향
- 제외 범위
- 산출물
- IA 요구사항
- 일정 및 제안 항목

## 디자인 방향

### 톤

- 엔터프라이즈 B2B
- ServiceNow / Salesforce 계열의 신뢰감
- 높은 정보 밀도
- 화려한 마케팅 랜딩 느낌 배제

### 시각 원칙

- 짙은 네이비/슬레이트 중심의 안정적인 팔레트
- 상태 강조용 청록/앰버/레드 액센트
- 타이포는 일반적인 스타트업 느낌보다 문서 친화적이고 제품스러운 조합
- 대시보드형 패널, 구조도, 승인 플로우, 테이블, 배지 중심

### 기억 포인트

이 사이트에서 가장 기억에 남아야 할 것은 “제안서인데 이미 제품 운영 구조가 보인다”는 감각이다.

## 시연 해석 기준

각 기능은 설명이 아니라 `시연 장면`으로 번역한다.

예시:

- 조직도/권한 관리
  - 동일 사용자가 회사 A와 B를 전환할 때 메뉴와 데이터가 바뀌는 장면으로 시연
- 결재 프로세스 빌더
  - 순차/병렬 단계가 보이는 플로우 캔버스로 시연
- 체크리스트/플레이북
  - 허용/금지 문구와 리스크 기준이 버전과 함께 보이는 관리자 테이블로 시연
- AI 리뷰 결과
  - 플레이북과 연결된 조항별 리스크 결과로 시연

## 테스트 전략

- 단위 수준: 핵심 데이터 구조와 체크리스트 개수/분류/상태 검증
- UI 수준: 주요 페이지에서 필수 섹션과 핵심 문구 렌더링 검증
- E2E 수준: 메인 → IA → 화면 전략 → 체크리스트 → 데모 플로우 이동과 핵심 메시지 검증

## 리스크와 대응

- 리스크: 정보량 과다로 페이지가 난잡해질 수 있음
  - 대응: 메인 페이지는 요약 중심, 상세는 보조 페이지로 분산
- 리스크: 요구사항 누락
  - 대응: 체크리스트 데이터 중심 설계
- 리스크: 제안서처럼만 보이고 제품 감이 약함
  - 대응: 각 섹션에 화면 프리뷰 및 시연 방식 병기

## 구현 원칙

- 처음부터 더미 데이터와 콘텐츠 모델을 먼저 만든다.
- 체크리스트 데이터를 단일 소스로 삼아 여러 페이지에서 재사용한다.
- 요청서에 없는 범용 설정이나 과한 추상화는 넣지 않는다.
- 시연 수준에 필요한 인터랙션만 구현한다.
